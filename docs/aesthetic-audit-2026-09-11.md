# Aoi Tori 美学综合审计与修复完善方案

日期：2026-09-11。对象：当前工作区的 Phase 5B 版本，而非仅 Git 已提交版本。

**结论：你的方向可以成立，而且比继续微调同一套青灰侧栏更接近本次目标。建议采用「左侧水彩青蓝 → 中央近白的阅读留白 → 右侧极淡的粉紫玻璃色」，并为深色单独设计「蓝灰 → 中性墨灰 → 微紫灰」的对应关系。当前浅色已有好的基础；深色需要调整大面积底色及层级，但没有证据支持把它定性为简单反色或文字对比度不合格。**

本文件是待实施方案，不表示这些候选颜色和布局已经装进主题、通过 Obsidian 实测或获得电影官方认可。此次只交付审计文档和计划记录。

### 1.3 与博客任务的关系

博客与 Obsidian 的共同问题是：不能只保证主背景漂亮，而让 Quote、Callout、表格、菜单和交互状态变回另一套颜色。可以沿用审计方法，但不能直接移植 Blowfish 的 CSS、RGB 调色表、卡片结构和 hero 规则。

## 2. 官方依据到底支持什么美学

### 2.1 官方创作表述

导演访谈强调透明、自然的空气感、小变化的积累，并在谈色彩时描述隔着玻璃观察的脆弱感。她也强调避免用简单符号代替人物细节。将这些转为 UI 原则，是本报告的设计推论：低饱和大面、清楚而克制的线条、间距与停顿，比大量主题贴图更能长期维持这种气质。[官方导演访谈](https://liz-bluebird.com/interview/)

两种声音的相邻、差异与短暂重合，也有官方关系描述的依据；但「蓝必须代表某个人，粉必须代表另一个人」不是官方 UI 规范，不宜硬编码为角色标签。[官方导演访谈](https://liz-bluebird.com/interview/)

### 2.2 官网真实的色彩结构

2026-09-11 在官网浏览器中读到：

| 官网区域     | 实际计算样式换算为 HEX   | 对本主题的用途                     |
| ------------ | ------------------------ | ---------------------------------- |
| Introduction | 横向 `#D3F4F8 → #FFEBF9` | 本次右侧淡粉紫及蓝粉邻接的主要参考 |
| Staff/Cast   | `#F7F9F9`，另有图形层    | 近白中性底面的参考                 |
| Ticket       | 横向 `#E6EFFF → #FFE3E3` | 辅助证明官网存在蓝与暖粉的关系     |

介绍区实际把文字放在白色多边形上，彩色环境留在周围。首屏则是另一幅插画，并非全站统一蓝粉背景。**本方案选择介绍区的空间关系作为“像官网”的具体含义，不把官网全部分区颜色搬入一个工作区。**

官网可见的轻薄碎片更接近玻璃／纸片状多边形，不宜把这一整组资源命名为羽毛。羽毛、蓝鸟和乐器组合，在官方「青い鳥チャーム」商品中有明确依据。[官网商品区](https://liz-bluebird.com/#goods)

### 2.3 指定水彩图的解读

这张图的主角周围是大量近白、带浅青的空间；水彩浓度不均匀，蓝色在少数地方聚集。人物附近的深蓝承担视觉锚点，不是背景主色。

因此，“左侧是这张图的水彩蓝”应理解为：

1. 使用背景中的淡青白及柔和蓝晕，而不是人物头发的深蓝。
2. 让白色仍占多数，不把侧栏整块涂成 `#83BEE7` 或 `#B8DEE8`。
3. 用一至两层静态、低强度的颜色变化暗示染色，不必模拟真实纸纹。
4. 水彩感来自颜色浓淡与空白的关系；一个完全均匀的青灰色块只能提供其中一部分。

本轮没有完成新的区域像素统计；沿用既有 `docs/visual-analysis.md`
的图像分类，但候选 HEX 均明确是 UI 设计值，而非声称从原图精确吸取的标准色。

### 2.4 应保留与应避免的视觉手段

| 目标     | 推荐手段                                   | 不推荐手段                               |
| -------- | ------------------------------------------ | ---------------------------------------- |
| 空气感   | 近白／低彩度大面，微小冷暖差，清楚的文字   | 将整个容器设低 opacity，导致文字一起变淡 |
| 水彩感   | 稀疏静态色晕，浓淡变化，大片干净空间       | 满屏纸纹、噪点、模糊滤镜                 |
| 两个声音 | 左右有差别，中间留出安静连接               | 左右完全相同，或一蓝一粉形成强烈色块对撞 |
| 音乐感   | 间距节奏，成对细线，少量主题 Callout       | 每个标题配音符、五线谱铺底、持续跳动     |
| 蓝鸟身份 | 小面积的蓝色动作锚点，一处有意义的鸟／羽毛 | 改掉所有导航图标、按钮状态和警告标志     |

## 3. 当前主题审计结果

### 3.1 已经成立的基础

- `--aoi-paper-warm: #FBFAF8` 是很好的长阅读底面；不需要为了“水彩”把正文整体染蓝。
- `--aoi-ink-indigo: #292B3B` 提供带色相的深墨色，正文不必改成纯黑，也不必再变淡。
- 浅色交互蓝 `#1D5FAE`、焦点蓝 `#1558A0` 有足够对比，可与环境色分工。
- Phase 5B 将云／雾／边界向青灰收敛，已减少过亮天空蓝的界面占比。
- 深色有独立的 primitives 和 semantic-dark 映射，未发现全局反色实现。
- 主题已经有 `[!aoi-tori]` 羽毛及 `[!second-voice]` 音乐图标，并非完全没有母题。
- Callout 已采用父层统一底色、正文正常文字色和透明内容层，不应重新引入嵌套白块／黑块。
- 警告、错误、成功、破坏性按钮有独立语义，必须保留。

### 3.3 关于 dark mode，哪些批评成立

**成立：**
夜间表面的色相过于集中，两个声音退化为蓝色底面加少量粉紫文字。它具有可用性，但与本次“水彩—玻璃—距离”的目标仍有明显距离。

**不成立或未被证明：**
“它只是浅色取反”“正文对比不足”“所有深色文字都糊”。当前静态正文对比为 13.97:1，链接为 6.79:1。若具体设备上仍觉得发糊，应另外检查字体、缩放、截图重采样、透明继承、显示设置和实际组件背景，而不是盲目提高字体亮度或把整个界面降透明度。

“夏夜”是项目以前的创作解释，不是官方要求。此次可以把它修正为更贴近纸、玻璃和暮色的夜间演绎，无须维护海军蓝这个实现结果。

## 4. 推荐的浅色方案

### 4.1 视觉构图

```text
左侧：稀释水彩青蓝       中央：近白阅读与桥接        右侧：微粉紫玻璃白
       青色逐渐收淡  ─────  空白保持宽阔  ─────  粉紫从远处轻轻出现
文件与导航                    笔记正文                    大纲／反向链接
```

建议采用一个宏观横向关系，而不是给每个面板重复一条完整的蓝粉渐变。可在工作区边缘、标签栏空白和编辑器外围看到过渡；正文核心仍有稳定底色。

中间不是左右 HEX 的算术平均。如果直接取较强青色与粉色的平均，容易产生一条存在感过高的灰紫带。更适合让两端同时向纸白收敛，形成较宽的明亮平台，再向另一侧展开。

### 4.2 候选色板

下面是第一轮原型值，需与当前版并排验收；不是官方取色表。

| 候选角色         | 建议值               | 使用位置                       |
| ---------------- | -------------------- | ------------------------------ |
| 左侧基础面       | `#EAF4F4`            | 左侧导航／环境底面，较现状更轻 |
| 左侧局部蓝晕上限 | `#DDEFF3`            | 左上或外侧少量区域，不作整屏底 |
| 中央过渡白       | `#F6F8F7`            | 两侧与编辑面之间的静态桥接     |
| 阅读纸白         | `#FBFAF8`            | 沿用现有正文主面               |
| 右侧基础面       | `#F5EFF4`            | 右侧大纲／反链背景             |
| 右侧局部粉紫上限 | `#EFE5EF`            | 边缘少量区域，不整栏高浓度覆盖 |
| 正文             | `#292B3B`            | 沿用                           |
| 链接／焦点       | `#1D5FAE`／`#1558A0` | 沿用，首轮不与环境同时调整     |

第一轮建议让左右底面自身承担色相差，再只叠约 3–6% 的局部语义色晕。不要同时使用强端点、强透明层和高彩度选中块。

### 4.3 渐变应怎样实现

优先实现“左右侧栏分区 + 中央外壳桥接”：

1. 左侧 split 使用独立左侧 surface/wash token，向内侧淡出。
2. 右侧 split 使用独立右侧 surface/wash token，向内侧淡出。
3. 中央外壳使用一条静态横向渐变，中间约 35–70% 为低彩度近白区。比例仅供原型使用，随窗口布局调整。
4. Markdown 编辑、Reading、Source 的主要阅读面保持现有纸白。更明显的连续渐变只放在外围或空白视图。
5. 标题栏、ribbon、标签栏和状态栏需要一起检查，避免上下两条旧青灰横带把左右关系截断。
6. 不对整个 `.workspace` 及所有后代设透明；当前 `.workspace-leaf-content`
   等有实色会遮住底层，必须按已检查的层次定向处理。
7. 菜单、输入框、tooltip、模态窗等交互表面仍应不透明；只让确认安全的装饰承载层透出环境色。

如果用户希望整张编辑页都能隐约看到连续渐变，可以作为第二个预览变体：正文区域的颜色跨度进一步压小，逐点验收文字和选中状态。推荐默认仍采用稳定纸面，因为多分屏、长文、图片和表格更可控。

### 4.4 为什么不建议把官网 HEX 原样铺满

官网更亮的蓝粉是为短时浏览、插画与大幅留白服务的；Obsidian 两侧有密集的小字、图标和选中状态。直接铺
`#D3F4F8 → #FFEBF9` 容易变成明显的彩色桌面。

参考官网的是颜色关系与白色承载方式；实际 UI 端点降低彩度，功能文字另有对比度要求。

## 5. 推荐的深色修复方案

### 5.1 目标

将“晴日颜色倒暗”改为“同一空间在光线降低后的独立表达”：左侧仍有一点冷水蓝，右侧保留极少的粉紫温度，中央是中性偏冷的墨灰纸面。亮色留给文字和当前动作。

这里的“夜间纸面”“暮色玻璃”均为原创设计解释；本次未找到可以作为官方 dark UI 规范的配色资料。

| 第二声部文字候选 | sakura/violet 两档 | `#C4B4C8` | 稀疏使用；不机械合并所有现有粉紫语义       |

建议先只换底面，保留 Phase 5B 的 `#8AADD9`
做一组对照，再尝试新链接色。否则无法判断改善来自底色还是交互蓝。

普通装饰边框允许柔和；输入轮廓、焦点、选中、图像操作等功能边界必须单独验证。候选普通边界色不能被当作已经符合 3:1 的交互边界。

### 5.3 候选静态对比度预检

采用 sRGB 相对亮度公式，按不透明文字／不透明纯色底计算；未包含渐变、透明层及原生控件继承。

| 前景               | 中央 `#222A30` | 抬升面 `#2C343C` |
| ------------------ | -------------: | ---------------: |
| 正文 `#E5EBEB`     |        12.08:1 |          10.47:1 |
| 次要文字 `#B8C4C8` |         8.16:1 |           7.07:1 |
| 弱文字 `#9DADB4`   |         6.29:1 |           5.45:1 |
| 链接 `#9CBED9`     |         7.48:1 |           6.48:1 |
| 第二声部 `#C4B4C8` |         7.43:1 |           6.44:1 |

预检说明该方向可以同时有柔和色彩与清晰文字，不表示最终界面已通过。

### 5.4 深色的局部 surface 规则

- Quote：优先接近阅读底，叠约 3–5% 的灰紫／玫灰，只让边缘提供第二声部。
- Properties：key 的浅紫灰与 value 的稳定面保持区别，不能把所有值输入区涂成彩色。
- Callout：保留原来的语义色，仅复核它们在新中性底上的强度；不把 Error/Warning 变成主题粉紫。
- Code：中性墨灰，区分正文靠轻微明度差、边界和排版，避免大块蓝黑凹槽。
- Active file/tab：正常、hover、selected 与 focused 要分开；选中不能只靠更亮的蓝块。
- Images/PDF：保持内容原色，不用主题滤镜处理用户文件，也不把白色 PDF 强行反色。
- 背景渐变：初始每区最多一至两层静态低强度 wash；没有发光、动画、噪点或 blur。
- 深色保留足够抬升明度；“安静”不等于主面、卡片、输入框全部揉成同一个灰。

### 6.2 公开主题与个人内容的边界

公开主题继续遵守仓库的独立项目身份。电影官网有权利署名，但本次没有找到允许把这些素材打进 MIT

因此：

- **公共默认方案：** 内置 Lucide 图标＋原创的抽象形状，README 以文字链接列出灵感来源。
- **若确实要原版官方素材：**
  先取得覆盖具体资源、修改、分发、宣传截图和使用场景的授权，再设计独立于 MIT 源码的权利清单。未取得前只列来源，不内置、不去水印、不热链。
- **个人 Vault 内容：**
  用户可自行决定如何使用其有权使用的图片；这些是笔记内容，不应自动进入主题包、示例库或宣传截图。不能以“个人使用”四字推定任意素材均获授权。
- **通用图标：**
  Lucide 许可页区分 ISC 主体和源自 Feather 的 MIT 部分；若复制文件，应保留相应声明。优先调用 Obsidian 已内置图标，可避免为了两枚图标加入运行时依赖。[Lucide 许可](https://lucide.dev/license)

### 6.3 推荐放置顺序

**第一优先：现有主题 Callout。** 无须先加资产即可使用：

```markdown
> [!aoi-tori] 一片羽毛放一段值得保留的短记。

> [!second-voice] 另一个声音放补充视角、对话或音乐笔记。
```

当前源码分别配置 `lucide-feather` 和
`lucide-music-2`。既有文档记录它们在 1.13.4 中解析成功，本轮未重新做图标注册表实测。官方允许通过
`--callout-icon`
指定内置图标，也提醒图标可用性取决于 Obsidian 所含版本。[Obsidian Callout 文档](https://obsidian.md/help/callouts)

**第二优先：可选的青鸟 Callout。** 可提议 `[!bluebird]`，用 `lucide-bird`，保留 `aoi-tori`
羽毛入口，不替换既有笔记行为。图标建议保持现有约 18
px 尺度，默认不与羽毛同时堆叠；解析失败就暂不新增该类型，不引入远程 SVG。

**第三优先：空白页的小签名。** 只在没有正文的空状态角落放一枚 24–40
px 原创羽毛或鸟，固定、不可交互、不靠近原生按钮。纯 CSS 主题不能任意注册页面、添加 DOM 或调用图标 API；如果当前空状态没有适合的稳定挂载结构，就先延期，不为这一点增加插件依赖。

**第四优先：音乐内容或说明页中的原创乐器。**
长笛与双簧管的辨识比泛用音符更有意义，但小尺寸完整乐器容易难认。优先在 48–80
px 的可选音乐说明卡中用原创线稿，或用两条不完全平行的细线表现二重奏。若使用自定义 Callout
SVG，应通过受支持的图标机制、继承语义色、记录来源，并先验证审计脚本是否兼容；本阶段不扩大默认安装包文件契约。

**不建议放置：**
每个文件夹、普通链接旁、正文水印、滚动条、搜索框占位符、图像缩放按钮、危险按钮、Canvas 每个节点。不要让羽毛取代警告、删除、展开和关闭的语义图标。

### 6.4 装饰预算

- 默认读写界面以现有 Callout 为主；页面级签名是可选项。
- 一个视口最多一处页面级具象母题；不限制用户在笔记里主动创建的语义 Callout 数量。
- 装饰低透明度只作用于装饰自身，不能降低标题和正文 opacity。
- 关闭装饰不应移除有语义的 Callout 标题、状态图标或焦点；“无装饰”与“无图标”是两件事。
- forced-colors 下去掉无意义装饰，保留所有功能线索；不做飘落、闪烁、鸟飞动画。

## 7. 工程修复设计

### 7.1 Token 分层

不要直接把现有 `--aoi-mist-blue`
改成粉紫，因为它还被输入、表格、菜单等多处使用。应为左右不同角色增加语义映射。

推荐接口草案：

```text
primitives.css
  新的冷青白、微粉紫白、中性夜灰、微紫夜灰等原始值

semantic-light.css / semantic-dark.css
  --aoi-workspace-left-surface
  --aoi-workspace-right-surface
  --aoi-workspace-bridge-surface
  --aoi-workspace-left-wash
  --aoi-workspace-right-wash
  --aoi-workspace-atmosphere-image

shell.css
  只消费这些角色，不写局部 HEX
```

这些名称是候选，尚未存在于实现。颜色值在 primitives；左右／中央语义在 mode 文件；角度、范围、强度等布局参数与既有配置体系保持一致。

要区分 `surface` 与
`wash`：surface 本身是完整不透明底色，wash 是叠加效果。关闭 wash 后不能因为底层没色而显示系统默认黑白。

### 7.2 CSS 层与变体冲突

| 场景                          | 必须处理的问题                                                                   |
| ----------------------------- | -------------------------------------------------------------------------------- |
| 左右叶子内部                  | 现有 leaf 自己有底色，可能把父渐变遮住；只透明经过验证的外壳层                   |
| 标签栏／状态栏                | 当前采用统一全局 token，需局部桥接或合理中性面，避免色带断裂                     |
| Style Settings sidebar tint   | Cloud/Mist/Aqua 必须有清楚定义；建议作为显式统一侧栏覆盖，而非悄悄压掉新默认     |
| Sky wash / Sakura / Violet    | 分清侧栏气氛、引用、属性三种用途，不让一个设置意外改整个工作区                   |
| Dark contrast / High contrast | 在新 primitives 上复查映射和优先级，不退回旧海军蓝                               |
| 两种关闭渐变设置              | 覆盖 workspace、Quote、Properties、Callout 与 HR；统一到一个装饰开关入口更易维护 |
| Forced colors                 | 新角色也映射到系统面，所有新增渐变去除；HR 有 `CanvasText` 等纯色回退            |
| 新空状态装饰                  | 不抢焦点、不拦点击、不增加滚动范围；样式不可作用于图像原生控件                   |

特别注意：HR 当前 `border: 0` 且依赖背景图。补 `background-image: none`
后还要补语义色底或边框，否则关闭渐变会让分隔线消失。

### 7.3 布局兼容

- 双侧栏打开：完整显示左右关系。
- 仅开一侧：中央仍稳定，不因缺少另一侧变成单色浓染。
- 双侧栏关闭：主体偏中性，只在外围保留可选微弱气氛。
- 多笔记分屏：横向关系属于窗口环境，不在每篇笔记重新开始整条蓝粉渐变。
- Pop-out：单独窗口也有默认色，不依赖主窗口的 DOM 祖先。
- Mobile：抽屉各有局部底色；正文保持中性。不把桌面完整渐变缩成 390 px 的彩条。
- RTL：明确左右是视觉方向的创作选择，还是导航／辅助区的语义选择；建议视觉左右跟随目标构图，功能内容顺序由 Obsidian 原生决定。需在支持 RTL 的目标版本实测。
- 窗口变宽：不拉伸成巨大的高饱和端点；检查带状渐变与显示器色阶，不默认用噪点掩盖。

### 7.4 完整组件范围

| 表面／组件                 | 本轮落地时要复核什么                                     |
| -------------------------- | -------------------------------------------------------- |
| 正文、H1–H6、粗斜体、链接  | 浅色不无故改动；深色在新背景上保持层级和非颜色线索       |
| Quote／Callout             | 标题、图标、正文、嵌套内容在同一底面逻辑中               |
| Properties                 | key/icon 同面，value 清晰；焦点和 hover 不被外壳渐变吞掉 |
| 表格／Bases                | 表头、hover、选择、编辑框明确，网格不过重                |
| Code／KBD／Tag／Highlight  | 辅助底色低彩度、文字清楚、语义颜色不乱改                 |
| 菜单／弹层／搜索／Settings | 实色承载，禁用与危险状态保持可辨                         |
| Graph／Canvas              | 更新需要的语义色，不让周边渐变进入原生绘制区域           |
| 图片／嵌入／PDF            | 容器适配，内容原色、操作和缩放保留                       |
| 手机底栏／键盘上方工具条   | 使用稳定底面和可用触控目标，不继承不合适透明层           |

## 9. 验收要求

### 9.1 美学验收

- 不打开示例插画，浅色也能辨认左青、中央近白、右微粉紫。
- 中央长文不是彩色渐变展示区，文字背后没有明显色带。
- 深色能看出同样的空间关系，整体不偏海军蓝、墨绿或褐紫。
- 背景安静，正文清楚，链接和焦点一眼可认。
- 去掉羽毛／鸟，配色仍成立；加上它们也不会像另一套贴纸皮肤。
- 同页看 10–15 分钟长文，检查眼睛疲劳、字重、标题跳跃和装饰干扰；记录主观反馈，不伪装成自动指标。

### 9.2 对比与交互验收

- 普通文字目标至少 4.5:1；必要图形及功能边界目标 3:1；装饰线与必要控件不要混算。
- 抽查渐变 0%、25%、50%、75%、100% 及局部色晕最浓位置，按实际叠层计算最差值。
- 对 hover、selected、focus、unresolved、code、tag、quote、callout、表格编辑和输入框分别检查。
- 同时存在选择填色与键盘焦点时，两个状态仍可区分。
- 装饰开／关、Sky 强度两端、Cloud/Mist/Aqua、dark contrast、高对比、forced-colors 均覆盖。
- 关闭渐变后 HR、Quote 边缘、输入框和活动项仍存在；不只看 `background-image` 是否为 none。
- 使用真实最终 CSS 检查，不以设计稿的颜色测量替代。

### 9.3 原生行为回归

按既有 `docs/TESTING.md`
流程重测受影响状态，包括：鼠标／键盘选图、复制／剪切／删除、grow／shrink／reset、Enter／Tab、Space／zoom
Lightbox、resize、Vim 命令、列表／引用／Callout／表格／嵌入内图片、pop-out、窄窗和手机触控目标。

不需要为了美学主动改动这些图像 selector，但外壳透明层、装饰伪元素和底色变化可能影响可见性，所以仍要做回归。

**代码要点：**

- 原生 `.theme-light/.theme-dark` 默认即为 Duet；不能只有 `body.aoi-sidebar-duet` 才有正确背景。
- Cloud/Mist/Aqua 除了现有原生变量，还必须显式设置新 left/right
  surface 为同一面，明确是否保持该旧选项的淡青 wash。推荐保持旧的淡青 wash 方向，同时将右侧 wash 设为同一冷色，以免形成旧底配新粉色。
- 三种旧浅色选项应让中央桥接回归中性，不继续露出粉紫端点；用 computed style 验证实际桥接层。
- `Sky wash intensity` 只影响 side wash 强度。Sakura 控制 Quote，Violet 控制 Properties；不得串用。
- “关闭水彩渐变”与“关闭装饰渐变”任一为开时都应去除装饰背景图，后者不删除或改 ID，保留旧设置兼容。
- dark contrast、高对比、stronger borders 在新 palette 上工作。禁止硬编码旧 HEX 回退。
- 修改 metadata 后检查生成 CSS 保留整个 `@settings`
  块。若实际设置项总数改变，同步 README；新增一个选项不等于新增一个设置项。

### 12.8 T05：层叠优先级、变量继承和关闭回退

**目标优先级（高到低）：**

1. 系统 forced-colors 的颜色／可见性保障。
2. 用户高对比、强焦点、强边界等必要可访问性设置；装饰关闭独立胜过任何装饰强度设置。
3. 明确的用户 palette／密度／组件选项。
4. `.theme-light/.theme-dark` 默认。
5. `:root` 通用基础值。

必须检查实际 specificity。`accessibility.css` 在最后导入，不代表里面低优先级 selector 自动能胜过
`body.theme-light.aoi-*`。使用最小且明确的 selector 匹配必要覆盖层级，不使用
`!important`，不全局清空样式。

**变量继承陷阱：** 若在 body 上定义
`--aoi-workspace-atmosphere-image: linear-gradient(...var(--aoi-workspace-left-surface)...)`，然后只在子 split 上改 left
surface，不能假定父元素已计算的派生变量会在子元素自动重新求值。稳妥实现是在相关配色变量同一元素作用域定义派生 image，或在消费层直接用所需 tokens 组装渐变。最终以 computed
`background-image` 为准。

**关闭规则的完整对象：**

- 新增的 workspace 桥接承载层、左右 split。
- Properties 的两层 wash。
- Quote 与 Callout 的 wash。
- `.markdown-rendered hr`、`.markdown-source-view.mod-cm6 hr`。
- 若 T07 引入的可选装饰有渐变，也必须覆盖。

两个旧设置 class 可以共享一个规则组，避免将来只修其中一个。保留当前语义 Callout 图标，不把“关装饰”实现成删除所有 icon。

**HR 的明确修法：**

1. 普通 HR 始终有 `background-color: var(--hr-color)`
   作为纯色回退，或使用等价可见 border；不得只依赖渐变。
2. 默认开启时允许继续使用现有背景渐变，但确认纯色回退不会破坏预期透明端部；必要时把实色仅放到关闭模式规则中。
3. 两个关闭设置各自触发 `background-image: none`，同时落到可见实色线。
4. forced-colors 内使用系统前景分隔色；不只是将 `--hr-color` 保持夜色蓝。
5. 验证 Reading 与 Live Preview；纯 Source 的 `---` 文本保留原生编辑表现，不强行创造图形节点。

**系统色的新 token：** left/right/bridge
surface 在 forced-colors 都使用 Canvas；派生渐变移除。强制颜色不应透出新左右粉蓝，也不应隐藏选中、焦点和输入框。

### 12.9 T06：移动、RTL 和弹出窗口的具体约束

移动已有入口：`body.is-mobile .workspace-drawer.mod-left`／`.mod-right` 及
`.workspace-drawer-header`。只调整抽屉外壳色彩；header 在对应抽屉内继承同一面，底栏和输入工具栏采用稳定中性面。

默认 mobile 不绘制横跨屏幕的完整蓝粉渐变。手机抽屉可保留极轻局部 wash，也可纯色回退；必须确保弹出动画中没有主面透穿。不改 safe-area、虚拟键盘定位、手势和 44
px 触控基线。

RTL 验收要区分代码的 `.mod-left-split` 与实际屏幕左边。若目标版本会镜像工作区，必须检查实际 bounding
rectangle 后建立映射；不能凭 class 名猜视觉方位。使用官方方向标记和已验证规则，原生功能顺序照常。无法验证时，报告 RTL 未测，不能添加猜测的双重翻转 CSS。

Pop-out 的编辑主面应自动继承当前 mode；无需为了没有左右栏的窗口强行加一对假侧栏。测试主窗口最小化时的图片缩放／Lightbox，不能只确认新窗口背景正确。

### 12.12 T09：验收失败如何处理

| 失败             | 优先修正                                           | 不可采用的“修复”                 |
| ---------------- | -------------------------------------------------- | -------------------------------- |
| 左侧像薄荷绿     | 减小绿相偏移或 wash 强度，保持亮度后对照原图       | 把整个页面改深蓝                 |
| 右侧像粉色主题   | 先减小 wash，再把基础面向中性白靠近                | 把第二声部全部删掉               |
| 中央出现灰紫带   | 加宽近白平台，降低端点彩度，检查是否多层叠加       | 给整页加模糊                     |
| 深色太闷         | 调主面与抬升面明度差，检查弱文字实际对比           | 无差别把全部文字改纯白           |
| 深色又像海军蓝   | 检查残留原始值与 overrides，降低大面彩度           | 对整个工作区使用滤镜             |
| 设置切换没效果   | 检查作用域、变量派生、specificity 与旧规则         | 加 `!important`                  |
| 第三方视图变透明 | 收窄透明 selector，恢复未知 view 不透明回退        | 增加更广泛透明规则               |
| 图标不存在       | 撤回新增类型或保留已验证羽毛入口，记录未完成项     | 热链 SVG、猜另一个 ID 然后不测试 |
| 手机出现横溢出   | 定位具体装饰／容器尺寸与定位，撤销导致溢出的新规则 | 全局 `overflow: hidden` 隐藏问题 |

每次调整都要记录“初始值 → 新值、改变原因、重测范围”。颜色可以改，但必须证明它解决了哪个失败，而不是反复凭名称替换。
